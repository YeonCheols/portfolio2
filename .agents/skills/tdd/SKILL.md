# TDD (Red → Green → Refactor)

## 요구사항과 소유권

- 연결된 이슈의 본문·댓글 또는 사용자 요구에서 기대 동작, 불변조건과 금지 사항을 확인합니다. 확인된 사실과 구현 후보를 구분합니다.
- 각 요구사항을 정상·경계·실패 시나리오, 구현 소유자, 대응 테스트에 연결합니다. 이슈에 없는 요구를 임의로 추가하지 않습니다.
- 기존 모델·타입·파서·정책·공통 함수를 검색하고 올바른 FSD 소유자에서 수정합니다. 호출자마다 같은 규칙을 복제하거나 원본과 파생 상태를 이중 관리하지 않습니다.
- 공유 로직을 바꾸면 생산자·변환·저장/캐시·소비자 중 실제로 연결된 경계와 인접 기능의 회귀 조건도 선정합니다.

## 체크리스트

```
- [ ] 1. 요구사항을 테스트 케이스 목록으로 정리 (정상/경계/예외)
- [ ] 2. Red: 실패하는 테스트 1개 작성 → 실패 확인
- [ ] 3. Green: 테스트를 통과하는 최소 구현 → 통과 확인
- [ ] 4. Refactor: 중복 제거/정리 → 여전히 통과 확인
- [ ] 5. 남은 케이스에 대해 2~4 반복
- [ ] 6. 관련 테스트 + pnpm lint 실행
```

## 원칙: 코드 수정 = 테스트 추가/수정

모든 코드 수정에는 **수정한 파일과 관련된 테스트 코드의 추가 또는 수정이 반드시 함께 포함**되어야 한다.

- 수정한 파일(`<name>.ts` / `<name>.tsx`)마다 대응하는 테스트(`<name>.test.ts` 또는 `<name>.test.tsx`)를 확인한다
  - 테스트 파일이 없으면 새로 만든다
  - 있으면 변경된 동작에 맞게 케이스를 추가하거나 기존 기대값을 수정한다
- 동작이 바뀌면 그 동작을 검증하는 케이스가 있어야 하고, 버그 수정에는 해당 버그를 재현하는 케이스가 있어야 한다
- 리팩터링처럼 동작이 바뀌지 않는 수정은 기존 테스트로 동작이 보호되는지 확인하고, 커버되지 않는 경로가 있으면 테스트를 먼저 보강한다
- 테스트 대상이 아닌 파일(페이지 thin wrapper, `index.ts` re-export, MDX 본문, `*.md`, 설정, 스타일만)만 바꾸는 경우는 예외다. 대신 완료 보고에 테스트를 추가하지 않은 파일과 그 이유를 적는다
- 테스트 없이 구현만 바뀐 상태로 작업을 끝내지 않는다

## 규칙

- 구현 코드보다 테스트를 **먼저** 작성하고 실패를 실제로 확인합니다. 미구현 동작이나 재현한 기존 버그 때문에 기대 결과가 어긋나야 합니다. 의존성 누락·잘못된 import·테스트 설정 오류는 해당 동작의 Red 증거가 아닙니다.
- 한 사이클에 테스트 1개만 추가한다
- Green 단계에서는 테스트를 통과시키는 데 필요한 코드만 작성한다
- 테스트를 통과시키려고 테스트 기대값을 바꾸지 않는다
- 테스트 통과만을 위한 fallback, 조용한 재시도, 느슨한 기본값, 테스트 전용 조건, 타입 단언·검사 무시로 원인을 덮지 않습니다. 필요한 호환 처리는 실제 계약과 소비자 근거를 확인합니다.
- Green이 실패하면 원인과 수정 가설을 확인하고 같은 테스트로 재검증합니다. 같은 실패가 원인 규명 없이 반복되면 무작정 재시도하지 않고 막힌 조건과 필요한 근거를 보고합니다.
- 브라우저와 네트워크가 필요한 화면 검증은 단위 테스트를 대체하지 않는다. 개발 서버는 사용자가 실행 중일 때만 확인한다

## 실행 근거와 임시 파일

- 각 사이클의 테스트 이름, 명령, 종료 코드, 실패 원인 또는 통과 결과를 기록합니다. 실제로 실행하지 않은 결과를 Red·Green으로 보고하지 않습니다.
- 출력 보관이 필요하면 작업 식별자가 포함된 고유 임시 디렉터리를 `mktemp -d`로 만들고 Red·Green 로그를 별도로 저장합니다. 파이프로 출력할 때 테스트의 종료 코드가 가려지지 않도록 확인합니다.
- 로그에 비밀값·환경변수 원문·실제 개인정보가 들어가지 않도록 가짜 fixture를 사용합니다. 임시 로그는 커밋하지 않습니다.
- 최종 보고에 결과를 요약한 뒤 현재 작업에서 만든 정확한 임시 경로만 정리합니다. 기존·추적 중·다른 작업의 파일을 덮어쓰거나 일괄 삭제하지 않습니다. 사용자 보존 요청 또는 진행 중인 리뷰가 로그를 필요로 하면 유지합니다.
- 커밋은 사용자 요청이 있을 때만 `commit` 스킬로 수행합니다. Red 상태에서 커밋하지 않으며 테스트와 구현을 함께 포함합니다.

## 파일 위치와 실행

- 단위 테스트: 대상 파일 옆 `<name>.test.ts(x)`
- Jest는 `next/jest`, `jest-environment-jsdom`, `@/` → `src/` 매핑을 쓴다 (`jest.config.js`)
- 단일 파일 실행: `pnpm test -- src/shared/lib/cn.test.ts`
- 감시 모드: `pnpm test:watch`
- 컴포넌트는 `@testing-library/react`로 렌더와 사용자 동작을 검증한다. 구현 세부(클래스 문자열 전체, 내부 state 변수명)는 단정하지 않는다

## 순수 함수 템플릿

```ts
import cn from "@/shared/lib/cn";

describe("cn", () => {
  it("falsy 값은 클래스 문자열에서 뺀다", () => {
    expect(cn("a", false && "b", "c")).toBe("a c");
  });
});
```

## 컴포넌트 템플릿

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

import { Button } from "./Button";

describe("Button", () => {
  it("클릭하면 onClick을 호출한다", async () => {
    const user = userEvent.setup();
    const onClick = jest.fn();
    render(<Button onClick={onClick}>저장</Button>);

    await user.click(screen.getByRole("button", { name: "저장" }));

    expect(onClick).toHaveBeenCalledTimes(1);
  });
});
```

## 테스트 작성 기준

- 테스트명은 한국어로 "~하면 ~한다" 형식
- 비즈니스 규칙, 분기, 빈 값, 에러 상태를 우선 검증한다
- API 클라이언트는 `fetch`/`axios`를 모킹하고 실제 네트워크와 `.env`에 의존하지 않는다
- 시각·난수는 제어 가능한 입력이나 mock으로 고정하고 변경한 환경변수·타이머·spy는 테스트 후 복원합니다.
- 구현 구조를 그대로 복사한 assertion 대신 사용자 동작과 데이터 계약을 검증합니다. 내부 함수만 통과해도 소비 경계에서 필드 손실·오래된 상태 덮어쓰기·개인정보 노출이 발생하는지 확인합니다.
- `pages/` 라우트 자체보다 `features/`와 `shared/`의 동작을 테스트한다
- 문서·설정 등 TDD 예외는 테스트 추가 생략 이유와 대체 검증을 적습니다. 설정은 필요에 따라 경로 해석·프로덕션 빌드·런타임 영향을 확인하며 예외를 안전성 검토 면제로 취급하지 않습니다.

## 완료 보고

다음을 요약한다.

- 수정한 파일과 그에 대응해 추가하거나 수정한 테스트 파일
- 사이클별로 추가한 테스트 케이스
- 테스트를 추가하지 않은 파일이 있으면 그 이유. 문장은 `~습니다`로 끝낸다
- 최종 `pnpm test` 결과(통과/실패 수)
- 이슈 요구사항과 테스트의 대응, Red·Green 명령과 결과, 인접 경계 검증 및 미확인 사항을 적습니다.
- 수정 후 `review` 스킬에서 목적·불변조건·회귀 영향을 재확인할 수 있도록 최신 작업 상태와 검증 범위를 적습니다.
