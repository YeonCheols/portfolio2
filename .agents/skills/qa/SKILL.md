# QA

## 범위 파악

`git status`, `git diff` (브랜치 단위면 `git diff origin/master...HEAD`)로 변경 파일과 영향 받는 feature(`src/features/<name>`, `src/pages`, `src/widgets`)를 확인한다.

브랜치 비교 전 `git fetch origin`을 수행하고 기준 SHA를 기록합니다. 이슈 본문·댓글 또는 사용자 요구의 기대 동작과 제약을 먼저 확인합니다. 실제 데이터 생산자·변환·저장/캐시·소비자와 공통 모델의 소유권을 따라 영향 범위를 정합니다.

## 1단계: 정적 검증

PR CI(`.github/workflows/ci.yml`)와 같은 명령을 사용한다. 로컬 QA는 빌드를 추가로 확인한다.

```bash
pnpm lint
pnpm format:check
pnpm type-check
pnpm build
```

- 포맷 실패는 `pnpm format`으로 고친 뒤 다시 검사하고, 자동 수정된 파일을 리포트에 명시한다
- `pnpm lint:fix`는 `yarn format`을 호출하므로 쓰지 않는다

## 2단계: 테스트

```bash
pnpm test
pnpm test --coverage   # 변경 파일 커버리지가 필요할 때
```

- 변경된 `src/**` 로직에 대응 테스트가 없으면 "테스트 누락"으로 기록한다 (필요 시 `tdd` 스킬 제안)
- 기존부터 실패하던 테스트는 이번 변경과 구분해 기록한다

## 3단계: 화면 / API 확인

개발 서버는 띄우지 않는다. 사용자가 이미 `pnpm dev` 또는 `pnpm dev:https`를 실행 중일 때만 확인한다.

- UI 변경: 영향 받는 페이지를 브라우저에서 열고, 주요 동작(클릭, 입력, 빈 상태, 다크 모드)을 확인한다
- `src/pages/api/*` 변경: 떠 있는 서버에만 요청한다. 비밀값과 토큰은 출력하지 않는다
- 서버가 없으면 "생략 (개발 서버 없음)"으로 적는다

## 4단계: 코드 리뷰

`review` 스킬(`.agents/skills/review/SKILL.md`)을 staged/branch/local 중 실제 변경 범위에 맞게 실행하고 발견 사항을 리포트에 그대로 옮깁니다. 미커밋 변경은 local 모드에서 staged·unstaged·관련 untracked 내용을 구분합니다. 일반 QA는 PR 댓글을 자동 작성하지 않습니다.

불변조건과 관련 시나리오를 확인·위반·미확인·해당 없음으로 구분합니다. 설정 변경도 모듈 해석·빌드·런타임·공개 노출 경계를 검토합니다. 테스트 통과만으로 서비스 전체를 확인했다고 쓰지 않습니다. 중요한 미확인은 검증 보류에 해당하는 차단 사항으로 기록하고, 수정 후 최신 상태에서 목적·변경·주변 영향·검증을 재검토합니다. MCP 도구는 로컬 호출·테스트를 기준으로 검증하며, 실제 MCP 서버 배포와 배포 후 호출 확인은 비차단 후속 제안으로 기록합니다.

차단 발견이나 중요한 검증 보류가 있으면 QA 결과는 실패로 기록합니다. 실제 MCP 서버 배포 및 배포 후 호출 확인의 부재만 남았다면 이를 비차단 후속 제안으로 기록하고, 나머지 결과에 따라 QA 상태를 판정합니다.

## 리포트 형식

```markdown
## QA 결과: <통과 | 조건부 통과 | 실패>

| 항목          | 결과       | 비고                |
| ------------- | ---------- | ------------------- |
| Lint          | ✅/❌      |                     |
| 포맷          | ✅/❌      |                     |
| 타입 체크     | ✅/❌      |                     |
| 빌드          | ✅/❌      |                     |
| 단위 테스트   | ✅/❌      | n passed / m failed |
| 화면/API 확인 | ✅/❌/생략 |                     |

### 발견 사항

- 🔴 반드시 수정: <파일:라인 - 내용>
- 🟡 권장: <내용>
- 🟢 참고: <내용>

### 다음 단계

<수정 필요 항목 또는 commit/pr 진행 제안>

### 불변조건과 미확인 사항

- <관련 시나리오의 기대 결과, 확인 상태와 근거를 적습니다.>
- <실행하지 못한 검증, 판정 영향과 필요한 최소 추가 검증을 적습니다.>
```

발견 사항과 생략 이유처럼 근거를 남기는 문장은 `~습니다`로 끝낸다. 발견 사항은 보고만 하고, 수정은 사용자가 요청하거나 명백한 린트·포맷 자동수정에 한해 진행한다.
